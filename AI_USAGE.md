# AI Usage & Collaboration Disclosure

This document outlines the tools, methodologies, human oversight, errors encountered, and correction workflows employed during the design, development, and testing of the School Admission System.

---

## 1. Architectural Planning & Stack Selection

- **Pen & Paper Initial Blueprint**: The fundamental entity relationships, state machines (`HELD` → `CONFIRMED` / `EXPIRED` / `CANCELLED`), concurrency boundaries, and UI wireframes were first planned manually on pen and paper.
- **HackMD Documentation**: The rough manual blueprint and project requirements were transferred to AI to structure an organized technical specification and working notes in HackMD.
- **Stack & Architecture Decisions**: Tech stacks were deliberately selected based on extensive real-world experience and optimal fit for high-concurrency race condition mitigation:
  - **Backend**: .NET 9 Web API (Clean Architecture with CQRS via source-generated Mediator, EF Core with PostgreSQL pessimistic row-level locking via `SELECT ... FOR UPDATE`).
  - **Frontend**: Next.js 15+ (App Router), React, Tailwind CSS, TanStack Query (real-time polling & state rehydration), Sonner (user feedback), and Lucide React.
  - **Database & Containerization**: PostgreSQL 16 on Alpine Linux, containerized with multi-stage Docker builds and Docker Compose.

## 3. Notable AI Mistakes & Human Corrections

While AI accelerated drafting boilerplate and repetitive code, human architectural oversight was essential to fix critical shortcomings:

### Mistake 1: Memory-Only Concurrency Checks vs. Multi-Instance Database Safety
- **The Issue**: Early AI code proposals attempted to count active holds using in-memory collections or simple LINQ queries (`CountAsync()`) without transactional locks. In a distributed multi-instance deployment sharing the same database, this created a textbook **Time-of-Check to Time-of-Use (TOCTOU)** race condition, permitting overselling.
- **Correction**: Replaced the naive check with an explicit database transaction utilizing **PostgreSQL pessimistic row-level locking** (`SELECT * FROM "Classes" WHERE "Id" = @id FOR UPDATE`). Added a schema-level **Partial Unique Index** (`IX_Holds_StudentId_ClassId WHERE "Status" IN (0, 1)`) so the database itself guarantees mathematical safety across distributed nodes.

### Mistake 2: Missing Header Checks Blocking Class List & Creation
- **The Issue**: Middleware generated by AI globally rejected any request lacking the `X-Student-Id` 17-digit header. This caused `GET /classes` (browsing classes) and `POST /classes` (admin class creation) to fail with `400 Bad Request`.
- **Correction**: Updated the endpoint filter middleware to explicitly bypass student header checks for public/admin routes (`/classes` on `GET` and `POST`), restricting the 17-digit BRN validation exclusively to student seat-holding, confirmation, and cancellation operations.

### Mistake 3: UI Breakpoints & Excessive Padding on Wide Displays
- **The Issue**: The frontend generator applied progressive utility classes (`px-4 sm:px-6 md:px-8 lg:px-12 2xl:px-16`) combined with a restrictive `max-w-[1920px] mx-auto` wrapper, resulting in massive empty side gutters on widescreen displays.
- **Correction**: Replaced the cumulative padding with a clean responsive scale (`px-4 sm:px-6 lg:px-8`), eliminated unnecessary max-width clamps, and ensured true full-width responsiveness across mobile, tablet, desktop, and ultra-wide screens.

### Mistake 4: Missing Test Dependencies & Native Rollup/Rolldown Bindings
- **The Issue**: When setting up the frontend test runner, the AI initially attempted Vitest, which suffered from Windows native binary incompatibility (`@rolldown/binding` / `std-env` ESM loader errors) with the local Node.js environment.
- **Correction**: Switched the test runner architecture to **Jest + ts-jest + @testing-library/react + @testing-library/jest-dom**, achieving clean, fast, 100% passing automated test execution across all components.

## 4. Human-in-the-Loop Philosophy

AI tools served as capable drafting assistants (functioning similarly to a junior pair-programmer). All architectural decisions, transactional consistency guarantees, security boundaries, and final code reviews were authored, directed, and verified by the engineer.
